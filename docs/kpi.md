# トオカエシ KPI定義（1ページ・2026-10-25）

デッキ第6・10項の「指標は1ページに固定」の実体。記録先は [kpi-weekly.md](kpi-weekly.md)。決定の経緯は [合議の決定記録](consensus/2026-10-25-kpi.md)。しきい値はここに書かず、デッキ第10項に従う。

## 指標（週次で記録する）
| 指標 | 定義式 | 出典・取得 | 区分 |
|---|---|---|---|
| 新規DL | 初回ダウンロード数（再DL・更新を除く） | ASC Sales and Trends。`scripts/weekly_kpi.py` で自動 | 実測 |
| 日表示 | AdMobの広告表示回数の日次合計 | AdMobコンソールから手入力 | 実測 |
| 日次広告収益 | AdMob推定収益の日次合計 | 同上 | 実測（判定の主役） |
| eCPM | 収益÷表示×1000 | 同上で計算 | 実測（参考。母数が小さい間は表示数と収益額を主に読む） |
| DAU | アクティブデバイス（日次） | ASC App Analytics（`scripts/app_analytics.py`）。report request 作成前・作成直後は「未取得」。代理で埋めない | 実測（同意ユーザー分のみ） |
| D1 / D7 | 継続率 | ASC App Analytics。インストール30件未満のコホートは「判定不能」 | 実測 |
| 1人日表示数 | 日表示÷DAU | DAU実測までは「代理」として日表示÷110〜220の幅（5〜10表示相当）で記録し、必ず「代理」と書く | 代理→実測に置換 |
| IAP | 購入件数と累計DL（件数のみ。比率は出さない） | ASC Sales | 実測（広告収益とは別枠） |
| 体験（最初の1局完走率・2局目開始率） | 計測手段なし | 枠だけ固定。値は「未計測」 | — |

各行にインストール母数（累計DL）を併記する。載せないもの: 端末内カウンタ由来の指標、比率単独、ランキング順位、レビュー平均、代理DAUからの月収益・10月eCPMの外挿。

## 表記ルール
- **欠損**: 取得できるはずの日に取れなかった。補間せず「欠損」と書き、件数を数える。集計では分母から除外する。
- **未取得**: 取得手段がまだない（例: App Analytics未作成、AdMob未入力）。理由と予定日を併記する。0や代理値で埋めない。
- **未計測**: 手段がなく、1ヶ月目は入れない決定のもの（体験指標）。推定値で埋めない。
- **未実施**: 定性観察をしなかった週。
- 直近約3日は判定に含めない（ASC公開遅れ、AdMob遅延）。判定の主は連続30暦日の単純平均。欠損が10日を超えたら判定せず保留（デッキは未決、合議で支持2・意見なし1）。

## 定性観察（週末尾に固定3行）
実機通しプレイ（起動から最初の1局の初手までのタップ数・秒数、遊び方に初見で着けたか）／周囲の観察（つまずき一言。ユーザー調査ではないので「ユーザーは〜」と書かない）／広告の見え方（自社バナーが宣伝に見えないか、結果ダイアログの裏に隠れていないか）。

## App Analytics の取得手順
- 必要: Admin か App Manager ロールのAPIキー（環境変数 ASC_ADMIN_KEY_ID / ASC_ADMIN_KEY_P8_BASE64、Issuerは ASC_ISSUER_ID）。Sales用の読み取りキーでは403になる。
- `python3 scripts/app_analytics.py create --yes` で ONGOING の report request を1件作る（書き込み。あんでぃさんの承認後のみ。1アプリ1件）。
- `status` で取得できるレポート（セッション・アクティブデバイス・継続率・DL元など）と日次instanceの範囲を確認、`fetch 名前の一部 [出力先]` でTSVを取る。
- データはリクエスト作成後（通常1〜2日）から貯まり始め、作成前の期間は遡れない。同意したユーザー分のみで、少数は集計から省かれることがある。

## 運用
- 週1・毎週月曜に1行追加する。ASC分は `python3 scripts/weekly_kpi.py` の出力（環境変数 ASC_* が必要。読み取りのみ）。
- AdMob分はあんでぃさんが週1で手入力する（APIは環境のネットワーク許可待ち）。2週続けて入力がなければ「保留」の合図とする。
- 停止基準: 記録が3ヶ月目末の判断に使えない（欠損10日超が続く）場合は記録の運用を見直す。
